# SQLite → Postgres Migration

Status doc + frozen architecture for the QuizAIPro data-layer migration.
Engine is selected at runtime: **Postgres when `DATABASE_URL` is set (Railway),
SQLite otherwise (local/dev/test).** The whole codebase keeps speaking SQLite
SQL through `db.get_conn()`; a thin compatibility layer translates to Postgres.

Verification model: SQLite path + the pure SQL translator are verified locally;
the live Postgres runtime is verified on Railway (no local PG in the build env).

---

## Stage 1 — FROZEN ✅ (dual-engine seam)

All in `db.py`. SQLite path is byte-for-byte unchanged (regression-tested).

- **`get_conn()`** branches on `DATABASE_URL`. SQLite → real `sqlite3` connection
  as before. Postgres → `psycopg.connect(..., row_factory=_pg_row_factory)`
  wrapped in `_PgConn`.
- **`_PgConn` / `_PgCursor`** present the exact `sqlite3` surface the 32 call-site
  modules use (`execute`, `cursor`, `commit`, `rollback`, `close`, context
  manager, `executescript`).
- **`_Row`** mimics `sqlite3.Row` — supports `row['col']` **and** `row[int]`,
  `.keys()`, `.get()`, `len()`, value-iteration — so no call site changes.
- **`translate_sql(sql, has_params)`** — pure, unit-tested. Translations:

  | SQLite | Postgres |
  |---|---|
  | `?` placeholders | `%s` |
  | literal `%` (e.g. `LIKE`) | `%%` (only when params present) |
  | `INSERT OR IGNORE` | `… ON CONFLICT DO NOTHING` (placed **before** any `RETURNING`) |
  | `ALTER TABLE … ADD COLUMN` | `… ADD COLUMN IF NOT EXISTS` (replaces the 45-site `except OperationalError` migration idiom — Postgres aborts a txn on a failed statement, so `IF NOT EXISTS` is required) |
  | `… INTEGER PRIMARY KEY AUTOINCREMENT` | `… INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
  | `PRAGMA …` | no-op |

  Deliberately **not** faked by the shim: `lastrowid` (Stage 2), `INSERT OR
  REPLACE` (Stage 3), `strftime` (Stage 4) — these are migrated at the call
  sites to forms that work on **both** engines.

## Stage 2 — `lastrowid` → `RETURNING id` — FROZEN ✅

All 46 sites converted (45 via a window-bounded, id-table-guarded transformer;
`api_v1/tests.py` idempotency site by hand). Verified on SQLite: every changed
file compiles, **zero `.lastrowid` remain**, plain `RETURNING id` inserts
round-trip through `db.get_conn()`, and the `OR IGNORE`+`RETURNING` idempotency
returns a row on insert / `None` on conflict. Diff is minimal (real changes only).


`cursor.lastrowid` has no Postgres equivalent. `INSERT … RETURNING id` works on
Postgres **and** SQLite ≥ 3.35 (Python 3.13 bundles 3.45), so every site converts
to a single portable form. **46 sites total.**

### Pattern report (file · table · RETURNING expression) — as executed

Every target table has `id INTEGER PRIMARY KEY AUTOINCREMENT`, so the expression
is **`RETURNING id`** in all 46 cases. Two sites need slightly more than a
mechanical swap (noted below).

| File | Sites | Tables |
|---|---|---|
| `app.py` | 27 | decks, users, cards, duels, chats, live_sessions, organizations, tournaments, study_groups, support_tickets |
| `seed_marketplace*.py` (4 files) | 8 | decks, cards |
| `api_v1/study.py` | 2 | decks/cards |
| `api_v1/tests.py` | 1 | test_attempts ⚠️ |
| `api_v1/{auth,jwt_auth,library,marketplace,tutor}.py` | 5 | users, refresh_tokens, decks, tutor_conversations |
| `goals.py`, `google_auth.py`, `seed_minitopics.py` | 3 | learning_goals, users, decks |

**Conversion forms**

- **Plain (44 sites):**
  `x = conn.execute("INSERT INTO t (…) VALUES (…)", p).lastrowid`
  → `x = conn.execute("INSERT INTO t (…) VALUES (…) RETURNING id", p).fetchone()[0]`
  (two-statement variants: add `RETURNING id`, change `cur.lastrowid` →
  `cur.fetchone()[0]`).

- **`app.py:1593` (users, read-at-distance):** `cur.lastrowid` is read a few
  lines later as a FK for a `group_members` insert. Capture the id into a local
  right after the users insert, use that local. (Not a risk — heuristic just
  flagged the nearer `group_members` line.)

- **`api_v1/tests.py:470` (test_attempts, idempotency) ⚠️:** `INSERT OR IGNORE`
  + `rowcount`/`lastrowid` dedup on `client_result_id`. Convert to
  `… RETURNING id`; the translator yields `ON CONFLICT DO NOTHING RETURNING id`.
  On conflict, `fetchone()` is `None` → that becomes the "already applied"
  signal (replaces the `rowcount == 0` check). Works identically on both engines.

Regression gate: after each batch, run the local SQLite round-trip test (insert
via the new `RETURNING id` form, assert the returned id is non-null and rows
persist).

## Stage 3 — `INSERT OR REPLACE` → upsert — FROZEN ✅

All 5 sites rewritten at the call site to `INSERT … ON CONFLICT (<pk>) DO UPDATE
SET …` (valid on SQLite ≥ 3.24 and Postgres). **Semantic note:** `OR REPLACE`
*resets* columns absent from the insert list; `ON CONFLICT DO UPDATE` *preserves*
them. Verified safe per site — the only unlisted columns (`stability`,
`difficulty` in the web flow) are overwritten by the very next `UPDATE`, and
preserving `repetitions` (mobile SM-2 state) on a web review is strictly better.

| File:line | Table | Conflict target | Resulting `ON CONFLICT` clause |
|---|---|---|---|
| `analytics.py:180` | `ip_geo_cache` | `(ip)` | `ON CONFLICT (ip) DO UPDATE SET country, country_name, region, city, timezone, isp, cached_at = excluded.*` |
| `app.py:2204` | `user_card_progress` | `(user_id, card_id)` | `… DO UPDATE SET ef, interval_days, reviews, lapses, due_at, last_grade, last_reviewed, is_favorite, is_difficult = excluded.*` |
| `app.py:2380` | `user_card_progress` | `(user_id, card_id)` | `… DO UPDATE SET ef, interval_days, reviews, lapses, due_at, last_grade, last_reviewed = excluded.*` |
| `app.py:2683` | `user_card_progress` | `(user_id, card_id)` | identical to `app.py:2380` (converted via `replace_all`) |
| `api_v1/study.py:609` | `user_card_progress` | `(user_id, card_id)` | `… DO UPDATE SET ef, interval_days, repetitions, reviews, lapses, due_at, last_grade, last_reviewed, is_favorite, is_difficult = excluded.*` |

Verified on SQLite: upsert **updates listed columns and preserves unlisted**
(`ef`→3.0 while `repetitions`/`stability`/`difficulty` retained). Zero
`INSERT OR REPLACE` remain.

## Stage 4 — date/time + remaining functions → `translate_sql` — FROZEN ✅

The Stage-0 audit's "18 strftime" were **Python `datetime.strftime()` calls**
(engine-agnostic — untouched). The real scope was **~60 SQLite-only SQL date
constructs** plus a few other functions. These are *systematic dialect
differences* — the same category as `?`, `INSERT OR IGNORE`, `AUTOINCREMENT`,
`PRAGMA`, which we already translate in `translate_sql` rather than rewrite in
source. So they are handled the same way: **source keeps SQLite syntax (runs
natively on the dev engine); `translate_sql` converts for Postgres.** All
translations preserve **TEXT result type** and **UTC** semantics, so downstream
code that expects `'YYYY-MM-DD'` strings and string-compares timestamps is
unchanged.

> ⚠️ **Interpretation of "zero SQLite-only date expressions remain":** they
> remain in *source* but are fully *handled* (translated) for Postgres — the
> consistent choice given the dual-engine design. Source-level removal of all
> ~60 is possible (~56 edits: `DATE(col)`→`substr(col,1,10)` etc. + Python-
> param rewrites for the `'now'` forms) but riskier (separator/timezone
> pitfalls) and inconsistent with how placeholders/AUTOINCREMENT are handled.
> **Flagged for your pre-Stage-5 review.**

| Original (SQLite) | Translated (Postgres) | Affected queries |
|---|---|---|
| `DATE(col)` | `to_char((col)::timestamp, 'YYYY-MM-DD')` | `GROUP BY DATE(...)`, daily-stat selects, dashboards (app.py, analytics.py, goals.py, api_v1/dashboard.py) |
| `DATE('now')` | `to_char((now() at time zone 'utc'), 'YYYY-MM-DD')` | "today" counters across admin/analytics |
| `DATE('now','-1 day')` | `to_char((now() at time zone 'utc') - interval '1 day', 'YYYY-MM-DD')` | "yesterday" counters |
| `datetime('now','-N days')` | `to_char((now() at time zone 'utc') - interval 'N days', 'YYYY-MM-DD HH24:MI:SS')` | 7d/30d windows, retention |
| `datetime('now','-N minutes\|hours')` | same w/ `interval 'N minutes'` | online-users, live presence |
| `strftime('%H', col)` | `to_char((col)::timestamp, 'HH24')` | `analytics.get_hourly_today` |
| `GROUP_CONCAT(x, sep)` | `string_agg(x, sep)` | `app.py:1567` (admin students list) |
| `instr(a, b)` | `strpos(a, b)` | `app.py:9815` literal-`\n` fix migration |
| `char(N)` | `chr(N)` | same migration (`char(92)`, `char(10)`) |

Also added: `_PgCursor.executemany` / `_PgConn.executemany` (for
`analytics.py:293` batch visit inserts). `RANDOM()` needs nothing (both engines).
Verified: translations unit-tested; SQLite still runs all natively; `to_char`
not mangled by the `char→chr` rule; full `py_compile` clean; consolidated
SQLite smoke (RETURNING + upsert + `DATE('now')` + executemany) green.

### Known Postgres risks (verify on Railway)
1. **`LIKE` case-sensitivity** — SQLite `LIKE` is case-insensitive (ASCII);
   Postgres `LIKE` is case-sensitive. ~50 `LIKE` sites (search, filters). **Not
   auto-translated** (a blanket `LIKE→ILIKE` regex risks corrupting string
   literals containing "LIKE"). *Decision needed:* targeted `ILIKE` for
   user-facing search, or accept case-sensitive search. **Highest-impact risk.**
2. **Type strictness** — SQLite has loose type affinity; Postgres is strict.
   Any place that inserts a string into an INTEGER/REAL column (or vice-versa)
   will error on PG. Mitigated by `RETURNING`/upsert testing, but worth a smoke
   pass over write paths.
3. **`executescript` multi-statement DDL** — `init_db`, `init_analytics_tables`,
   `init_billing_tables` run big `;`-separated blocks via one
   `_PgCursor.executescript` → one psycopg `execute`. Valid in psycopg3 but
   verify the full schema applies in one shot on a fresh PG.
4. **Timestamp text format** — columns store text (`isoformat()` with `T`, or
   `'YYYY-MM-DD HH:MM:SS'` with space). Translations preserve string-compare
   semantics, but the boundary instant of `>=` windows depends on the separator
   exactly as it already does on SQLite (no regression, but a known sharp edge).
5. **Transaction abort semantics** — a failed statement aborts the whole PG
   transaction (unlike SQLite). The `ADD COLUMN IF NOT EXISTS` translation
   removes the main offender; watch for any other `try/except` around DDL/DML
   that assumed SQLite's per-statement tolerance.

### Tables requiring special handling (data copy)
- **Identity reseed** — every `id … AUTOINCREMENT` table (33) becomes IDENTITY;
  after copying rows with explicit ids, run `setval(pg_get_serial_sequence(...))`
  so new inserts don't collide.
- **`user_card_progress`** — composite PK `(user_id, card_id)`, no identity;
  straight copy.
- **Junction/no-id tables** (`group_members`, `chat_members`,
  `collection_decks`, `study_group_*`, `*_members`) — composite PKs; straight
  copy, no sequence reset.
- **`ip_geo_cache`** — text PK `ip`; straight copy.
- **FK ordering** — copy parents before children (organizations → users →
  decks → cards → progress/reviews → …) or defer FK checks during load.

## Stage 5 — Data copier — BUILT ✅ (PG run pending on Railway)

`migrate_sqlite_to_pg.py` + `test_migrate_copier.py`. Run on Railway:
`DATABASE_URL=… python migrate_sqlite_to_pg.py --init --yes`.

- **FK-safe order** — topological sort from SQLite `PRAGMA foreign_key_list`
  (parents before children); cross-cycles tolerated.
- **Clear-first** — target tables are emptied children-first before copy, so
  `init_db`-seeded bookkeeping (`app_migrations`) doesn't collide; copier is
  idempotent / re-runnable.
- **Id preservation** — explicit ids inserted (IDENTITY is `GENERATED BY
  DEFAULT`, so explicit values are allowed).
- **Self-referential FKs** — `categories.parent_id`, `refresh_tokens.replaced_by`
  copied via a null-then-update two-pass (order-independent).
- **Identity reseed** — `setval(pg_get_serial_sequence(t,'id'), MAX(id))` for the
  33 id-autoincrement tables, so post-migration inserts don't collide.
- **Verification report + row-count validation** — per-table `src` vs `dst`
  counts; any mismatch → non-zero exit.

Verified SQLite→SQLite (no PG in the build env): 51 tables, correct FK order,
self-ref values + ids preserved, counts match. **Not yet run against Postgres**
(psycopg connect, `%s` paramstyle, `setval` reseed) — that's the Railway gate.

### Bugs found & fixed by this validation (would have broken cutover)
- **Schema column drift** — `init_db`/analytics/billing under-create columns that
  ALTER-migrations (in app startup) add (`decks.color`, `name_uz`, …). Fix:
  copier `ensure_schema` builds the target **from the source's own DDL**
  (SQLite stores ALTER-added columns in `sqlite_master`), guaranteeing parity.
- **FK orphans** — SQLite doesn't enforce FKs, so the source has orphan rows
  (`cards.deck_id` with no `decks` row) that PG rejects. Fix: copier sets
  `session_replication_role=replica` for the bulk load.
- **SQLite JSON funcs** — `json_object`/`json_group_array` (in `dashboard.py`)
  don't exist on PG. Fix: `translate_sql` → `json_build_object`/`json_agg`.
- **Type strictness** — `api_v1/study.py` stringified integer ids
  (`card_id=str(...)`); PG rejects non-numeric/empty strings for int columns.
  Fixed that site (coerce to `int`); see risk below — this class is app-wide.

### Failed queries / acceptance-gate results (`test_phase2-6.sh`)
The phase tests were executed against the app on the embedded PG. Results are
**inconclusive** because the portable PG binaries ship an **incomplete `share/`
(no `timezonesets`/tzdata)**, so the backend crashes on some timezone operations
(`FATAL: could not open directory ".../timezonesets"`), dropping connections and
cascading `auth/register` 500s into every phase. This is an embedded-proxy
packaging defect, **not** an app/migration defect. Phase 6 (validation/auth-only)
was **62/0**. The data-flow phases must be **re-run on real Railway PG**.

Real app issues the gate did surface before the proxy crashes: the JSON-func gap
(fixed) and the integer type-strictness class (one site fixed). Note: `get_conn`
opens a connection per call with **no pooling** (272 `get_conn` vs 447 `.close()`
— closing is fine, but per-request connections will pressure PG under load).
